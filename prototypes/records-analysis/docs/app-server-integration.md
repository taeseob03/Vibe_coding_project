# 앱 화면과 서버 연결 안내

## 현재 화면

- 메인: 내 캐릭터, 네 활동의 횟수·단계, 아래쪽 작은 `게시` 버튼.
- 게시: 팝업에서 글·사진·둘 다 입력 → 실제 Gemini 분석 → 메인 캐릭터와 라운지의 내 캐릭터 갱신.
- 오른쪽 스와이프: 메인에서 라운지로 이동. 왼쪽 스와이프는 메인으로 돌아감. PC는 상단 탭 사용.
- 라운지: 멤버의 캐릭터가 자동 이동. 이동 조작·일시정지·위치 초기화 기능 없음.
- 친구: 닉네임 검색 → 초대 → 수락 대기 → 수락한 사용자만 라운지 멤버로 표시.
- 받은 초대: 수락/거절. 수락 시 해당 친구의 라운지로 이동하고 참여 라운지 목록에 추가.

로그인·캐릭터 생성이 끝난 사용자가 접속한다는 가정이다. 로그인과 최초 생성 화면은 이번 구현에 포함하지 않았다.

공동 저장소의 개발 연결 모드에서는 A의 실제 로그인·최초 생성 화면을 거쳐 `/app`으로 들어온다.
`backend/app/preview`가 인증된 프로필과 계정별 테스트 스택 저장을 연결하며, 친구 기능은 예제를 유지한다.
`/api/frontend-config.js`가 계정별 공개 프로필을 설정하므로 초기 예제의 user-1 대신 실제 UUID를 사용한다.
계정·캐릭터 기존 테이블과 스택 테스트 저장소를 합치는 최종 운영 통합은 별도이다.

## 역할과 교체 지점

| 담당 | 작업 |
|---|---|
| 서버 담당 | 인증, 내 프로필·사용자 검색, 기록 저장, 캐릭터 누적 저장, 초대/멤버십 권한 및 트랜잭션 |
| 디자인 담당 | 캐릭터 생성 과정, 몸체·소품·배경 자산, 최종 색상·크기·레이어와 애니메이션 |
| 현재 앱 구현 | 화면 전환, 게시·결과·오류 표시, 검색·초대·수락 화면, 서버 API 어댑터와 캐릭터 렌더러 연결 |

기존 계획서의 A/B 세부 분담은 초기 계획이다. 앞으로는 위 역할에 맞춰 연결하며, 공통 API 규약은 서버 담당과 합의한다.

- `static/api.mjs`: 모든 HTTP 호출과 예제 초대 저장을 모은 어댑터.
- `static/app-config.mjs`: API 경로와 친구 기능 모드 설정. 비밀 키를 넣지 않는다.
- `static/social-model.mjs`: 예제 사용자·초대 상태 전이. 실제 서비스의 권한 검증을 대체하지 않는다.
- `static/character.mjs`: 메인 캐릭터 표시와 임시 자산 목록.
- `static/lounge-view.mjs`: 라운지 멤버 갱신·자동 이동·효과 동반 표시.
- `static/style.css`: 최종 디자인을 적용할 화면 스타일.

## 현재 예제 모드의 동작과 범위

`socialMode: 'demo'`가 기본이다. 내 사용자 ID는 `user-1`이며 민지·준호·서연은 가상 사용자다.
처음에는 내 라운지에 나만 있다. 민지에게서 받은 예제 초대 1건이 있다.
초대·수락·참여 라운지는 이 브라우저의 localStorage(`campus-social-demo-v1`)에 저장되며 새로고침 후 유지된다.
지원되는 브라우저에서는 Web Locks로 같은 브라우저의 탭 간 변경을 직렬화하고 storage 이벤트로 다른 탭의 변경을 갱신한다.
다른 기기나 브라우저에는 공유되지 않는다. 실제 친구에게 초대 메시지가 전송되지 않는다.

라운지 아래 `초대 수락 테스트 → 친구의 수신함 열기`에서 수신자를 선택해 수락/거절을 시험한다.
서버 모드에서는 이 테스트 기능과 예제 안내가 숨겨진다. 실패 시 예제 모드로 자동 전환하지 않는다.

게시 분석은 예제가 아닌 기존 `/api/keywords`와 SQLite 누적 저장을 이용한다.
현재 로컬 백엔드는 로그인 없는 공용 프로필 1개이다. 사용자별 서비스를 위한 인증·DB 격리는 서버 담당과 통합해야 한다.
원본 글·사진은 현재 저장하지 않고, 분석 결과(요약 포함)·해시·누적만 저장한다. 실제 게시물 저장/복구는 서버 연결 단계에서 추가한다.

## 서버 API 제안

아래 경로는 새 화면의 제안이며, 공동 저장소의 기존 규약을 임의로 변경한 것은 아니다.
실제 서버 경로가 다르면 `app-config.mjs`와 `api.mjs`에서 맞춘다.

| 요청 | 응답/역할 |
|---|---|
| `GET /api/me` | `{id, nickname, emoji}` 로그인한 사용자. 실제 ID는 UUID |
| `GET /api/progress` | `{progress:[{category,count,level,color,icon,...}]}` 현재 사용자의 네 활동 |
| `POST /api/keywords` | multipart `record_id`, `text`, `image`. 분석 결과와 최신 `progress` |
| `GET /api/lounges` | 참여 중인 배열 `[{id,owner_id,name}]` |
| `GET /api/lounges/{id}/members` | `[{id,nickname,emoji,counts:{술:0,공부:0,연애:0,운동:0}}]` |
| `GET /api/users?nickname=검색어` | 검색 결과 `[{id,nickname,emoji}]`. 본인 제외, 결과 수 제한 |
| `POST /api/lounges/{id}/invitations` | JSON `{recipient_id}`. 서버가 sender를 인증 정보로 결정 |
| `GET /api/lounge-invitations` | 배열 `[{id,room_id,sender_id,recipient_id,status,sender:{nickname},recipient:{nickname}}]` |
| `POST /api/lounge-invitations/{id}/response` | JSON `{accept:true 또는 false}` |

프런트는 쿠키 기반의 동일 출처 인증 요청(`credentials: same-origin`)을 사용한다.
Bearer 토큰 방식을 합의하면 공통 `request()`에만 토큰 전달을 추가한다. 쿠키 인증은 서버의 CSRF 보호 정책도 함께 맞춘다.
오류 형식은 공동 저장소의 `{error:{code,message}}`를 지원하고, 기존 로컬 API의 `{detail:문자열}`도 읽는다.

실제 기록 API를 `/records`와 비동기 분석으로 연결할 경우 어댑터가 저장 → ID/대기 반환 → 상세 폴링 → 완료 결과 정규화를 담당하도록 바꾼다.
화면은 현재 동기 결과를 기다리므로, 폴링 취소·페이지 이탈·재시작 복구를 같이 구현해야 한다.

## 서버가 보장할 규칙

- 현재 사용자/발신자/수락자는 클라이언트 ID가 아닌 인증 정보로 결정한다.
- 라운지 멤버만 목록을 조회하고, 주인만 초대하도록 현재 화면과 동일하게 제한한다.
- 자기 자신, 없는 사용자, 이미 참여한 멤버, 중복 대기 초대는 거부한다.
- 초대 수신자만 수락/거절한다. 수락 처리와 멤버 추가는 한 트랜잭션으로 저장한다.
- 초대·멤버십은 DB UNIQUE 제약으로 중복을 방지한다. 이미 처리된 초대에 대한 재요청 정책을 명시한다.
- 기록당 활동 1회만 누적한다. AI 분석·효과 지급 상태를 분리하고, 효과 복구 때 AI를 재호출하지 않는다.
- 확정된 술 기록은 술 +1, 운동 스택 -1이다. 운동은 최소 0이며 해당 기록의 최초 반영 시 한 번만 차감한다.
- 차감 당시 운동이 0이면 미래의 운동 스택을 미리 차감하지 않는다. 누적 이벤트의 적용 순서를 보존한다.
- 운동 스택이 5→4, 10→9가 되면 디자인 단계도 내려가며, 0이면 운동 소품을 표시하지 않는다.
- stack_changes에는 해당 요청으로 실제 반영된 변화만 반환한다. 기록 재시도에는 비워서 반환한다.
- 관계없는 키워드와 불확실한 분류는 누적을 보류한다.
- 기록/사진 크기 제한과 소유자 접근 권한은 서버에서도 검증한다.

위치 이동은 각 클라이언트의 연출이다. 두 기기의 이동 좌표가 같아야 하는 단계에서는 WebSocket과 서버 방 상태를 별도로 연결한다.

## 확인 방법

1. 서버 실행 후 메인에서 `게시`로 글·사진을 분석하고 누적과 캐릭터 변화를 확인한다.
2. 메인에서 오른쪽 스와이프하거나 `라운지` 탭을 누른다.
3. `친구 초대`에서 `민지` 검색 → 초대. 이 시점에는 나만 표시되어야 한다.
4. 초대 창 닫기 → `초대 수락 테스트` → 친구 수신함에서 민지로 수락. 민지가 라운지에 추가된다.
5. 준호도 같은 방식으로 수락하면 세 명이 함께 이동한다.
6. `받은 초대`에서 민지의 예제 초대를 수락하면 민지의 라운지로 이동한다.
7. 새로고침 후 누적·초대·참여 라운지가 유지되는지 확인한다.

자동 검증: `npm ci` 후 `npm test`, Python 의존성 설치 후 `python -m pytest -q`.
JS 테스트는 jsdom 기반 화면 이벤트/DOM 검증이며 실제 브라우저에서 터치·레이아웃을 관찰한 검증과는 다르다.
